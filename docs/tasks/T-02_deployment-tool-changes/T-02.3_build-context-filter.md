## Goal

`prepare_context` copies the whole service folder into the Docker build context with an ignore list of `.git`, `__pycache__`, `.venv`, `windows`, `.env`, `*.pyc` (F9). The pattern `.env` matches only that exact name, so `.env.staging` and `.env.production` (which tts has locally and must never be opened) would be copied into an image layer, and so would a `testclear/` venv. Close that.

## Specification

- Add to the ignore patterns: `.env.*` **except `.env.example`** (use an ignore function, not only `shutil.ignore_patterns`, to keep the example), and `testclear`. Keep every existing pattern.
- A generic tool should not know tts: do not add `models` here. A native deploy on the same machine leaves the voice in the service's `models/` folder; copying it into the context is harmless (the `prepare` step then finds it) and is noted as such.

### Result (2026-11-06; edits in `D:\Hobbys\IA\OBLIVION\deployment`, nothing committed)

**Can the tool's service directory contain these files at all?** Not through the tool. The tool clones the service into `<workdir>/services/<repo>` and a clone holds only tracked files. `git ls-files '.env*'` (names only) in the eight service repositories: only `.env.example` in tts, brain, microphone, stt, speaker, ai-agent and camera; `.env` and `.env.example` in stepper (a generated `.env` that is tracked, already excluded by the old `.env` pattern). In tts `.env`, `.env.staging` and `.env.production` are git-ignored (`.gitignore:94: .env*`) and untracked. So the filter is defence in depth for a work directory that is a hand-made working folder (the case the audit worried about), and for a service that later tracks such a file by mistake. No `.env` file was opened for this check.

**Built.** `infrastructure/outbound/runtime/docker_runtime.py`: a public function `context_ignore(directory, names)` replaces the inline `shutil.ignore_patterns(...)` of `prepare_context`. It keeps every old pattern (`.git`, `__pycache__`, `.venv`, `windows`, `.env`, `*.pyc`), adds `testclear`, and adds every name that starts with `.env.` except `.env.example`, at every level of the tree. `models/` is deliberately not excluded (a generic tool does not know tts; after a native deploy on the same machine the voice travels into the context, which is harmless and noted in the manual). LF kept; no other file of the tool changed.

**Tests** (`tests/test_docker_context.py`, new, 19 tests, no Docker; a fake service tree with a `SimpleNamespace` host and a stub shell): the service files, `.env.example`, `docs/`, nested folders and `models/` are copied; `.env`, `.env.staging`, `.env.production`, `.env.local`, `.env.anything` and a nested `.env.staging` are not (parametrized); `.git`, `.venv`, `windows`, `testclear`, `__pycache__` (also nested) and a stray `.pyc` are not; the text of the secret files appears in no file of the context; requirements and wheels are added; an older context is replaced, not merged; a dry run copies nothing. A first run of the new file failed before the change (8 failures: `.env.*` and `testclear` were copied) and one failure after it was a bug of my fixture (it wrote the secret text into `.env.example` too), fixed.

**Mutation check** (scratch script in the session scratchpad; the file restored after each run, hash verified): 11 one-line changes, all caught: the `.env.<name>` rule dropped; the example dropped too; only `.env.staging` dropped; `testclear`, `windows`, `.venv`, `.git`, bytecode and plain `.env` each no longer excluded; `copytree` with no ignore at all; the old context kept instead of removed.
