## Goal

Today `deployment/docker/service.Dockerfile` runs the `prepare` script with `|| echo "warning: prepare step failed"`, so an image without the Piper voice builds fine and falls back to pyttsx3 silently (F8, debt D-6). Make the failure fail the build for the services that say their `prepare` step is required, and keep the warning for the native path and for every other service.

## Specification

- The native path is unchanged: a failed `prepare` warns and the deploy continues (a machine that was offline must still come up).
- Dockerfile shape (one line of intent, not a prescription): `python $PREPARE || { echo "..."; [ "$PREPARE_REQUIRED" != "1" ]; }` so that a required step returns non-zero and fails the `RUN`.
- `fetch_voice.py` exits 0 when `TTS_ENGINE` is not `piper` (F7), so "required" cannot break a build for another engine. The build runs with the service's default settings (no `.env` exists then, F8): the default engine is Piper, so the voice is fetched and required. Record the limitation that a user who wants only `espeak` in Docker still needs network at build time.
- The failure message must name the script, the exit code and the next step ("check the network and build again").
- Settings stay in one place: `prepare_required` is a fact about the service, so it lives in the catalogue, not in a layout or a local file.

## Acceptance criteria

- A catalogue test: `tts` has `prepare_required == True`; a service without the key has `False`.
- A unit test of `docker_runtime.build` shows `PREPARE_REQUIRED=1` in the `docker build` arguments for tts (using the fake `Shell`; `--dry-run` still has no side effects).
- The generated command for a service with `prepare` but without `prepare_required` is exactly as before.
- The deployment suite passes.

Run the deployment tests in the background. The real behaviour (a build that fails offline) is proved in [T-03.4](../T-03_docker-and-arm64-acceptance/T-03.4_build-without-network.md), because it needs Docker.
