## Goal

When tts answers `is_available: true` with a `reason` (the fallback note of T-01.2.2), the tool must say so. Today `http_health.check` reads `is_available` and the `reason` only when it is `false`, so a fallback prints "healthy and available" and nobody sees it (D-6).

## Specification

- If `is_available` is `true` and `data.reason` is a non-empty string, `check` still returns `ok = True` but the detail becomes `healthy and available, warning: <reason>`. The deploy and the start continue (ADR-006).
- If `is_available` is `false`, the behaviour is exactly as before, including the short grace period.
- The reason is shown as text from a service on the maintainer's own network: truncate it to a sensible length (for example 200 characters) and print it on one line.
- This depends on T-01.2.1 having chosen option A. For option B (new fields), the same function reads the new fields; update this task before starting.

## Acceptance criteria

- Tests: available with a reason → `ok` and a detail containing `warning:` and the reason; available without a reason → detail exactly `healthy and available`; unavailable with a reason → as today.
- The deployment suite passes.

### Result (2026-11-06; edits in `D:\Hobbys\IA\OBLIVION\deployment`, nothing committed)

**Both paths go through `check`** (read in `application/services/deployment_service.py`): `start`, `deploy`, `update` and rollback call `wait_healthy`, which calls `HealthPort.wait`, which loops on `check`; `status` (local) and `status --remote` call `check` directly; the remote wait before a start (`wait_for_remotes`) also calls `check` and only looks at `ok`. So the change is in one function, `infrastructure/outbound/health/http_health.py`, and `deployment_service.py` was not touched. `start`/`deploy` print `<name>: <detail>`; `status` prints `<detail>; <branch>@<commit>; <runtime>` in its row.

**Built.** In `check`: when the service is available and its `data.reason` is a non-blank string, `ok` stays `True` and the detail is `healthy and available, warning: <reason>`; the reason is made one line (whitespace collapsed) and cut to `REASON_MAX_CHARS = 200` characters (197 and `...`). Unchanged: unavailable (with or without a reason, including the 15 s grace in `wait`), available without a reason (exactly `healthy and available`), a service without a `ready` endpoint (`healthy`, never reads a reason), a reason that is not text (ignored). A fallback is not "unavailable", so `wait` returns at once and neither deploy nor start fails or waits because of it (ADR-006, ADR-008). Only `http_health.py` changed in code (LF kept).

**Tests** (`tests/test_health_wait.py`, 1 to 16 tests, against small local HTTP servers): reason shown as a warning and `ok`; no reason, `null`, empty and blank give exactly `healthy and available`; no `reason` field at all; a non-text reason (number, list, dict, bool) is ignored; unavailable keeps `available: <reason>` / `available: not available`; a multi-line 500-character reason becomes one line of exactly 200 characters ending in `...`; a reason of exactly the limit is not cut; no `ready` endpoint gives `healthy`; `wait` returns at once with the warning (under 5 s); the adapter's `check` and `wait` give the same detail (so `status` and `start` agree). **Mutation check** (scratch script in the session scratchpad; the file restored after each run, hash verified): 10 one-line changes, all caught: warning branch never taken; a fallback makes the check fail; a blank reason is shown; a non-text reason is read; limit 100; cut keeps 3 characters too many; newlines kept; warning wording changed; unavailable text lost; no-ready service reports available. A first version of the long-reason test would not have caught limit 100; it now asserts exactly 200.
