## Goal

Build `oblivion/tts:local` with the deployment tool (or the same `docker build` command it runs) on amd64, with Python 3.12 (the Dockerfile default), and see that the `prepare` step fetched the voice into the image.

## Read first

The preconditions of [T-03](T-03_docker-and-arm64-acceptance.md), `deployment/docker/service.Dockerfile`, `deployment/README.md` (Docker).

## Files

None changed. The tool builds in its own work directory (`<workdir>/build/tts`).

## Steps

1. With the maintainer's yes (network, disk, about 1 GB of layers), set tts to `runtime = "docker"` in `deployment/config/local/tts.toml` (the maintainer's own file; restore it at the end) and run `oblivion.py deploy --host <machine> -s tts`, **or** build by hand from the tool's context folder: `docker --context desktop-linux build --build-arg APT_PACKAGES="espeak espeak-data libespeak1" --build-arg PREPARE="scripts/fetch_voice.py" --build-arg PREPARE_REQUIRED=1 -f deployment/docker/service.Dockerfile -t oblivion/tts:local <context>`.
2. Read the build output of the `prepare` step: it must show the voice fetched and "ready".
3. Check the image holds the voice: `docker --context desktop-linux run --rm --entrypoint ls oblivion/tts:local -l /app/models`.
4. Note the image size and the build time.

## Acceptance criteria

- The build succeeds; the `RUN` of the `prepare` step shows `Piper voice en_GB-alan-medium is ready`.
- `/app/models` holds `en_GB-alan-medium.onnx` and `.onnx.json`.
- `pip` installed `piper-tts` and onnxruntime without compiling anything on Python 3.12.

## Verification

The relevant lines of the build output, the `ls` output, the size and the time, in *Notes*.

## Notes

Python 3.12 has not been exercised for tts before (the tested versions are 3.11 and 3.14); if an install fails on it, record the package and the message, and decide with the maintainer whether to change `PYTHON_VERSION` for this service (a catalogue setting) rather than patch the Dockerfile.

**Acceptance.** All three criteria met: the build succeeds and the `prepare` step shows `Piper voice en_GB-alan-medium is ready`; `/app/models` holds both voice files; pip installed `piper-tts` and onnxruntime on Python 3.12 without compiling.

**Findings.**
1. **What the image contains is the pushed commit's requirements**, not the working tree: pytest 9.2.0, ruff 0.17.4, black 26.10.1, mypy 2.4.1 and httpx 0.28.1 are in the image (the split of T-01.3 is uncommitted), and contracts-microservice 0.15.0 (the working tree has 0.16.0). This build therefore says nothing about the new fallback `reason`; it is in none of the pushed code. A later image built from the working tree (or from a commit holding it) is needed for T-03.2 to see the `reason`; committing is the maintainer's call.
2. The tool's `prepare_context` and the real Dockerfile worked together on the first real run: `COPY . /app`, `requirements.docker.txt` with the `-e ../shared-logging` line removed, the wheel from `libs/`, and `./vendor/...whl` resolved from `/app`.
3. The image is large for a service that needs about 60 MB of voice plus Python: 792 MB, of which onnxruntime/numpy and the voice are the bulk; the dev tools add a part that the split will remove. Not measured further.
4. A cosmetic Docker warning at the top of the log (a `pip` root-user warning and a pip upgrade notice) is not a problem.
5. The container was not started and nothing was published; `oblivion/tts:local` stays in the local Docker Desktop image store for T-03.2. The clone and context stay in the scratchpad (`t031`) until T-03 is finished.
