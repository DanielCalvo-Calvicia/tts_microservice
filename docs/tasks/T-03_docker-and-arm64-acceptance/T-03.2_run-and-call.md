## Goal

Run the image the way the tool runs it and check that tts answers from another address, speaks with Piper, and that the tool shows a fallback if there is one.

## Read first

`deployment/infrastructure/outbound/runtime/docker_runtime.py` (`start`: the `.env` is bind-mounted read-only at `/app/.env`, the port is published on the machine's bind address), [T-01.1.3](../T-01_deployment-readiness/T-01.1_baseline-checks/T-01.1.3_log-and-endpoint-checks.md).

## Files

None changed.

## Steps

1. Start the container with the tool (`oblivion.py start --host <machine> -s tts`), or by hand with the same arguments as `docker_runtime.start`.
2. `docker --context desktop-linux logs oblivion-tts`: it must contain `Piper voice loaded`, and must not contain `falling back`.
3. From **another machine** (or the host's LAN address, not `127.0.0.1` inside the container): `GET /health`, `GET /available`, `POST /process/batch?text=hello&sample_rate=24000`.
4. `oblivion.py status --host <machine>`: tts is healthy, with no `warning:`.
5. Fallback case: start a second container of the same image with `TTS_PIPER_VOICE` set to a missing voice in the mounted `.env`; `status` must show the `warning:` of T-02.2 and the log the fallback line.

## Acceptance criteria

Steps 2 to 5 give the stated results; the audio is non-empty, 24000 Hz, mono.

## Verification

The log lines, status codes and `status` output, in *Notes*.

## Notes

Remove the second container and restore any setting you changed.

**Step 2, container log:** `Piper voice loaded voice="en_GB-alan-medium" sample_rate=22050`, `TtsService initialized ... engine="PiperSpeechSynthesis"`, `Uvicorn running on http://0.0.0.0:8002`; **0** `falling back` lines. (Container logs are JSON lines.)

**Step 3, endpoints**, on `http://127.0.0.1:8002` and on `http://192.168.1.9:18002` (the host's LAN address; not from another machine: none was used): `GET /health` `200 {"healthy":true}`; `GET /available` `200 {"is_available":true,"reason":null}`; `POST /process/batch?text=hello&sample_rate=24000` `200`, rate 24000, channels 1, 28,300 bytes (localhost) and 31,278 bytes (LAN), 24,464 and 26,634 non-zero bytes. (The byte count varies from call to call: Piper is not deterministic.)

**Step 4, `oblivion.py status --host robot ... -s tts`:** `tts  running  healthy and available; feature_ai_claude_2@54a6259a; docker` (no `warning:`, as expected; the commit shown is the clone's, the code is the working tree's).

**Step 5, the fallback (a missing voice in the mounted env, run through the tool's `start`):** the log has `Piper unavailable; falling back to pyttsx3` (ERROR, `reason="Piper voice 'en_XX-nothing-medium' is not in /app/models (...)"`) and `engine="Pyttsx3SpeechSynthesis"`. But **the tool did not show a warning: it failed** (exit 1, `status` `UNHEALTHY`): `GET /available` answered `is_available: false` with the reason `fallback: pyttsx3 instead of piper (Piper voice 'en_XX-nothing-medium' is not in models (...))`, and `POST /process/batch` answered **502** (`pyttsx3 ... SetVoiceByName failed with unknown return code -1 for voice: gmw/en`). **Cause (found by probing throwaway containers, nothing saved):** the image's apt packages `espeak espeak-data libespeak1` are the old espeak 1.48 (voice data has `voices/en`, no `gmw/...`); pyttsx3 2.99's espeak driver asks for the voice name `gmw/en` (an espeak-ng name) when it cannot read the current voice and old espeak refuses it. In the image as built the pyttsx3 fallback **fails**, while the service's own `espeak` engine works (`/usr/bin/espeak`, 19,962 samples at 22,050 Hz). With `espeak-ng espeak-ng-data libespeak-ng1` added in a throwaway container, **both work** (pyttsx3 saved a 26,620-byte WAV; the espeak engine used `/usr/bin/espeak-ng`). So in this Docker image ADR-006's promise, "the service always starts **and speaks**", does not hold: it starts, reports `is_available: false` and cannot speak, and Brain's preflight would fail on it. This is debt **D-11** (new). The tool behaved correctly: it reported the unavailable service with the reason.

**The `warning:` branch of T-02.2 against a real fallback.** Because the container's fallback is broken, the "available with a reason" case cannot occur in the image. It was shown with a real tts process on Windows (pyttsx3/SAPI works there): a copy of the working tree without any `.env*`, started on port 8013 with a missing voice; `GET /available` gave `{"is_available":true,"reason":"fallback: pyttsx3 instead of piper (...)"}` and the tool's own `http_health.check` and `wait` returned `True | healthy and available, warning: fallback: pyttsx3 instead of piper (Piper voice 'en_XX-nothing-medium' is not in models (...))`. It was not run through `oblivion.py start/status` on Windows (that was a direct call of the tool's health function).

**Acceptance.** "Steps 2 to 5 give the stated results; the audio is non-empty, 24000 Hz, mono": steps 2 to 4 do (audio 24000 Hz, mono, non-empty; the LAN check was on the host's own LAN address); step 5 does **not** (the fallback is not healthy in the image). The task therefore stays **in-progress** until the maintainer decides about D-11. Not covered either: access from another machine.
