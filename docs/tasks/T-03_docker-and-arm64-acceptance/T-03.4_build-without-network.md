## Goal

Prove that the strict build of T-02.1 fails loudly when the voice cannot be downloaded.

## Read first

[T-02.1](../T-02_deployment-tool-changes/T-02.1_fail-the-docker-build.md), [T-03.1](T-03.1_amd64-build.md).

## Files

None changed.

## Steps

1. Build the image with the dependency layers cached (so only the `prepare` step needs the network), but make the voice fetch fail. At build time there is no `.env`, so the voice name cannot come from the settings; pass a voice that does not exist through the build argument instead: `--build-arg PREPARE="scripts/fetch_voice.py --voice en_XX-nothing-medium"` (keep `PREPARE_REQUIRED=1`).
2. Expect the `RUN` of the `prepare` step to fail, the message to name the script and exit code, and `docker build` to end non-zero.
3. Rebuild without the wrong argument: it succeeds.

## Acceptance criteria

The build fails in step 2 with a readable message and no image is tagged `oblivion/tts:local` from the failed attempt; step 3 succeeds.

## Verification

The failing output lines and the exit code (`$LASTEXITCODE`), in *Notes*.

## Notes

A real offline build is also possible (disconnect the machine after the layers are cached), but it depends on the maintainer's network; the wrong-voice route proves the same code path.

### Result (2026-11-06, Docker Desktop 29.5.2, `--context desktop-linux`; the maintainer said "Yes, T-03.4")

**Setup.** The build context was regenerated with the tool's own code from the working tree (216 files, only `.env.example`, nothing forbidden), with the arguments the tool generates now: `PREPARE_REQUIRED=1`, `PREPARE=scripts/fetch_voice.py`, `APT_PACKAGES=espeak-ng libespeak-ng1`. Every build below used `-t oblivion/tts:local` and the tag's image id was read before (`sha256:3be3e06d4a06...`) and after each build. Logs are in the session scratchpad (`t036_A.log`, `t036_B.log`, `t036_D.log`, `t036_C.log`).

**Build A, the task's route** (`--build-arg PREPARE="scripts/fetch_voice.py --voice en_XX-nothing-medium"`, network available, apt layer cached): **`docker build` exit 1** (107 s; the pip layer re-ran for 96 s because `docs/` had changed since the previous build, so "dependency layers cached" held for apt only). The `prepare` step printed `Fetching Piper voice en_XX-nothing-medium into /app/models (about 60 MB)`, `Could not fetch Piper voice en_XX-nothing-medium: HTTP Error 404: Not Found`, `The service will start with the pyttsx3 voice until it is there.`, then the new Dockerfile message: `error: the prepare step 'scripts/fetch_voice.py --voice en_XX-nothing-medium' failed with exit code 1 and this service requires it. Check the network and build again.` Docker ended with `ERROR: failed to build: failed to solve: process "/bin/sh -c if [ -n \"$PREPARE\" ]; ..." did not complete successfully: exit code: 1`. The tag `oblivion/tts:local` still pointed at the same image id afterwards.

**Build B, an extra: `--network none`** (same arguments): exit 1 in 9 s, but it failed in the **apt** step (`#6 ERROR`), not in `prepare`: BuildKit includes the network mode in the cache key, so the cached layers were not reused and `apt-get` could not run. It proves nothing about `prepare` and is recorded only so that nobody repeats it. The tag was unchanged.

**Build D, a real connection failure in the voice step** (extra): `--build-arg HTTPS_PROXY=http://127.0.0.1:9 --build-arg HTTP_PROXY=http://127.0.0.1:9` (predefined build arguments: they do not invalidate the cache) with `PREPARE="scripts/fetch_voice.py --voice en_GB-alan-low"`, a real voice that is not in the context. Layers #6 to #9 were `CACHED`, the voice step ran and printed `Fetching Piper voice en_GB-alan-low ...`, `Could not fetch Piper voice en_GB-alan-low: <urlopen error [Errno 111] Connection refused>`, the hint line, and the same `error: the prepare step ... failed with exit code 1 and this service requires it. Check the network and build again.`; **exit 1 in 2 s**; the tag was unchanged. This is what an offline build produces in the voice step (a connection error, not a 404).

**Build C, step 3: the correct arguments** (no wrong voice, no proxy): **exit 0 in 18 s** (layers #6 to #9 cached; `prepare` `Piper voice en_GB-alan-medium is ready in /app/models`, found in the context's `models/`). `oblivion/tts:local` now has a new image id (`sha256:2ef5e642d5de...`), 663 MB, because the copied `docs/` changed since the earlier image; `:worktree` (`3be3e06d4a06`) and `:pushed` are unchanged. One dangling image remains from the rebuild.

**Acceptance.** Met: the build fails (A and D) with a readable message that names the script, the exit code and the next step; no image was tagged from a failed attempt (the id of `oblivion/tts:local` was identical after A, B and D); step 3 succeeds. **Not done:** a build on a machine that is really offline (the maintainer's network was not disconnected), and a failing build started through `oblivion.py deploy` (the hand-run `docker build` used the arguments the tool generates; the tool's own code path for building was exercised in T-03.1 and T-03.2). Because the wrong voice/proxy changes `PREPARE`, the build's failure path was shown, not the specific "no `.env`, default voice" case; the code path is the same (`fetch_voice.py` exits 1, the `RUN` fails).

**Finding.** `fetch_voice.py` takes the voice name from `--voice` or the environment, so the build can be steered by `PREPARE` (the catalogue); nothing in the image hard-codes the voice except the default.
