## Goal

Decide how a running tts tells a tool that it is speaking with a fallback voice, without breaking Brain's preflight (ADR-006: the service must start and speak on the fallback).

## Facts

- `GET /available` answers `AvailabilityResponse(is_available, reason)`, and `GET /health` answers `HealthCheckResponse(healthy)`; both dataclasses come from `contracts.api.microservices.common` (F5), shared by every service.
- `AvailabilityResponse` **already has an optional `reason`**. tts never sets it.
- Brain reads `/available` in its preflight (`brain_microservice/.../health_check.py`, `http_client.py`). Whether Brain ignores a `reason` when `is_available` is `true` must be read there before the choice is applied (note it here).
- The deployment tool waits on `/available` (`ready = "/available"`, F10).
- A fallback must not turn `is_available` into `false`: Brain's preflight would exit and take the robot down, which ADR-006 forbids.

## Options

| | Option | Cost | Shows the engine when healthy | Shows a fallback |
|---|---|---|---|---|
| A | Use the existing `reason` of `AvailabilityResponse`: `is_available` stays `true` and `reason` carries the fallback note (for example `fallback: pyttsx3 (Piper voice en_GB-alan-medium is not in models)`); `reason` is empty when the chosen engine is the one speaking | tts only; no `contracts` change | no | yes |
| B | Add `engine` (and `fallback`) fields to `AvailabilityResponse` in `contracts` | a `contracts` change and version bump, re-bundled in every service (CLAUDE.md rule) | yes | yes |
| C | No API change: the Docker and deploy checks read the log for `Piper voice loaded` | none | no | only by log scraping |

**Recommendation: A.** It is the smallest change that closes the silent case, needs no new contract field, and cannot break a consumer that already ignores `reason`. The healthy engine name stays in the log (`TtsService initialized`, `engine=PiperSpeechSynthesis`). Choose B only if you want the engine name on every `/available`.

## Questions for the maintainer

1. A, B or C?
2. If A or B: should `GET /health` stay exactly as it is (liveness, touches no engine)? Recommended: yes.
3. Should the deployment tool show the `reason` as a **warning** (deploy continues) or fail `deploy`? Recommended: warning; the Docker build is made strict separately (T-02.1).

## Reading of Brain's handling of `reason` (2026-11-06)

`brain_microservice/infrastructure/outbound/http/http_client.py:47-61` (`check_health`): Brain calls `GET /health` (must be 200), then `GET /available` (must be 200), parses `AvailabilityResponse`, and **reads `reason` only when `is_available` is false**: `return ExternalHealthResponseDto(False, f"available: {availability.reason or 'not available'}")`. When `is_available` is true it returns `ExternalHealthResponseDto(True, "healthy and available")` and ignores `reason`. `application/services/health_service.py:40` and `voice_pipeline/steps/health_check.py:39` only carry `is_available` (and the detail). Consequences: a `reason` on an `is_available: true` answer **cannot break Brain's preflight** (option A is safe), and Brain will **not show** the fallback in its own log or status; the deployment tool (and people reading `/available`) would be the only readers. The words "healthy and available" printed by the deployment tool in T-01.1.2 and T-01.1.4 are the same detail string. A change on the Brain side (to log the reason when present) would be a separate task in the `brain_microservice` repository, not part of this plan.

## Resolution

**Decided by the maintainer on 2026-11-06**, all three recommendations:

1. **A**: the existing `reason` of `AvailabilityResponse`; `is_available` stays `true` on the fallback; no `contracts` change.
2. `GET /health` stays exactly as it is (liveness, touches no engine).
3. The deployment tool shows a fallback `reason` as a **warning**; `deploy` continues. The Docker build is made strict separately (T-02.1).

Recorded in [ADR-008](../../../decisions/ADR-008-fallback-reported-in-available-reason.md) (new, with its row in the index of `docs/decisions/README.md`) and as a dated note in [ADR-006](../../../decisions/ADR-006-fallback-and-voice-at-deploy-time.md). The reading of Brain's handling is above. T-01.2.2 and T-02.2 are unblocked.
