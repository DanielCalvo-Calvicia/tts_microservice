## Goal

Show, on a real deploy, what happens when the Piper voice cannot be fetched: the deploy must warn, the service must still start and speak on pyttsx3, and a second deploy with a valid voice must repair it. This is the behaviour of ADR-006 and the evidence for debt D-6.

## Read first

[../../../decisions/ADR-006-fallback-and-voice-at-deploy-time.md](../../../decisions/ADR-006-fallback-and-voice-at-deploy-time.md), `deployment/docs/DEPLOYMENT.md` (the tts section and "Voice files").

## Files

None changed in the repositories. The drill uses a **local settings file** of the deployment tool, `deployment/config/local/tts.toml` (the maintainer's own, never committed); create or edit it, and restore it at the end.

## Steps

1. Set a voice name that does not exist (for example `TTS_PIPER_VOICE = "en_XX-nothing-medium"`) in `config/local/tts.toml`, and make sure no voice of that name is in the deployed `models/`.
2. `oblivion.py deploy --host pc` (ask first). Expected: the `prepare` step warns (`Could not fetch Piper voice ...`), the deploy continues, tts starts.
3. `oblivion.py logs --host pc -s tts -n 100`: expect `Piper unavailable; falling back to pyttsx3` with a `reason`.
4. `GET /available` and `POST /process/batch?text=hello&sample_rate=24000`: record what they answer. Expected today: `is_available: true` and audio from pyttsx3 (the silent case).
5. Restore `config/local/tts.toml` and `deploy` again with network: the voice is fetched, the log shows `Piper voice loaded`.

A "no network" variant (disconnect the machine) is the second best drill and needs no settings edit; use it if the maintainer prefers.

## Acceptance criteria

Steps 2 to 5 behave as expected, with the exact `deploy` warning text, the log line and the answers of `/available` recorded in *Notes*; the settings file is restored.

## Verification

The pasted warning, log line and answers.

## Notes

Compare the warning text with what T-02.1 and T-01.2.3 will change: the exit code and wording of `fetch_voice.py` are the inputs of those tasks.

### Result (run on 2026-11-06 with the maintainer's yes, native, Windows, same throwaway deployment as T-01.1.2)

**How the drill was set up.** Not by editing `deployment/config/local/tts.toml` (that file does not exist in the repository and was not created): the drill used a `local/tts.toml` in the **throwaway config** of T-01.1.2 (`--config`, scratchpad `t0112`) with `[env]` `TTS_PIPER_VOICE = "en_XX-nothing-medium"`. `oblivion.py env ... tts` confirmed `TTS_PIPER_VOICE=en_XX-nothing-medium    # config/local/tts.toml`. The deployed `models/` held only the real voice, none named `en_XX-nothing-medium`.

**Step 2, `deploy` with the bad voice** (exit code **0**; paths shortened to `<T>`):
```
$ <T>\work\venvs\tts\Scripts\python.exe scripts/fetch_voice.py
Could not fetch Piper voice en_XX-nothing-medium: HTTP Error 404: Not Found
The service will start with the pyttsx3 voice until it is there.
Fetching Piper voice en_XX-nothing-medium into <T>\work\services\tts_microservice\models (about 60 MB)
warning: tts: `scripts/fetch_voice.py` failed (1); see above
tts: started in its own window (pid 27056)
tts: healthy and available
```
The warning is shown, the deploy continues, tts starts, and the last line is **`healthy and available`** (the deploy output ends as for a good deploy). (The "Fetching" line prints after the error only because stdout and stderr are interleaved.)

**Step 3, log** (`oblivion.py logs ... -s tts`), as ERROR:
```
Piper unavailable; falling back to pyttsx3  reason="Piper voice 'en_XX-nothing-medium' is not in <T>\work\services\tts_microservice\models (fetch it with: python scripts/fetch_voice.py from the service folder, or deploy again)"
TtsService initialized  name="TTS Microservice" engine="Pyttsx3SpeechSynthesis"
```
followed by `TTS availability probe returncode=0` from `pyttsx3_subprocess`.

**Step 4, the answers on the fallback** (the silent case, evidence for D-6):
- `oblivion.py status`: `tts  running  healthy and available; feature_ai_claude_2@54a6259a; native`, identical to the Piper case.
- `GET /available`: `200`, `data` = `{"is_available":true,"reason":null}`, identical to the Piper case.
- `POST /process/batch?text=hello&sample_rate=24000`: `200`, 24000 Hz, 1 channel, **69,776 bytes** (about 1.45 s, 25,986 non-zero bytes) against 30,286 bytes (0.63 s) from Piper for the same word. Audio from pyttsx3 (Windows SAPI voice). Nothing in the answer tells the caller which engine spoke.

**Step 5, restore and repair.** `local/tts.toml` of the throwaway config removed; `env` then showed `TTS_PIPER_VOICE=en_GB-alan-medium    # defaults`. The two voice files were first deleted from the deployed (scratchpad) `models/` so that the repair really fetches (otherwise the good voice would still be on disk and nothing would be fetched). `deploy` again (exit 0): `Fetching Piper voice en_GB-alan-medium ... (about 60 MB)`, `Piper voice en_GB-alan-medium is ready`, `tts: stopped`, `tts: started in its own window (pid 27808)`, `tts: healthy and available`. Log: `Piper voice loaded voice="en_GB-alan-medium" sample_rate=22050`, `TtsService initialized ... engine="PiperSpeechSynthesis"`. `batch` gave 200 / 24000 / 29,292 bytes. Both files are back in `models/` (63,201,294 and 4,888 bytes). One listener on 8002 and no leftover process of the earlier runs.

Acceptance: steps 2 to 5 behave as expected; the exact warning, the log line and the `/available` answers are above; the drill settings file is removed (the repository's `config/local/` was never touched).

### Findings (inputs of T-01.2, T-02 and T-03)

1. **D-6 reproduced end to end:** a failed voice fetch gives a warning in the middle of the output, exit code 0, `healthy and available` in the deploy and in `status`, `is_available: true` with `reason: null`, and a different engine behind it. Only the log line (ERROR, with a `reason`) and the byte count of the audio tell the engines apart.
2. **The warning is easy to miss and the final line contradicts it.** Candidates for T-02.2: make `status` and the readiness wait name the engine, and end the deploy summary with the warning when a `prepare` step failed.
3. **`fetch_voice.py` exits 1 on a missing voice and prints a message that already says the consequence** ("The service will start with the pyttsx3 voice until it is there."); T-01.2.3 pins the exit codes with tests.
4. **The log file is appended across restarts** (the first run's lines were still there, with older timestamps). A check that greps the log for `falling back` must look only at the lines after the last `Started server process`, or the check will report an old fallback or hide a new one. Relevant to T-01.2.4, T-02.2 and T-03.
5. **A configured voice that is missing falls back even though another good voice is on disk** (`models/` still held `en_GB-alan-medium` during the fallback). By design (the voice named in the settings is what is loaded), but it is the same situation as the Docker case in the audit, where `.env` is mounted at runtime and names another voice than the one baked into the image.
6. The first drill deploy did not print `tts: stopped` before starting (the second did); the old process had gone and only one listener remained, so no harm. Not investigated.
