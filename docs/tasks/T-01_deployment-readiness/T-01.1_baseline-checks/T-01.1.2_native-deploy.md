## Goal

Deploy tts with the deployment tool on a clean machine layout, the way the robot will really be deployed, and see that the `prepare` step fetched the voice.

## Read first

`deployment/CLAUDE.md`, [../../../deployment/deployment.md](../../../deployment/deployment.md), `deployment/docs/USER_GUIDE.md` (the commands), `deployment/config/catalogue.toml` (the `[services.tts]` entry, F10).

## Files

None changed in this repository. The tool writes in its own work directory (the cloned services, the `.env` of each service, the logs). Do not edit `deployment/config/` for this check: use a layout and a `config/local/` that already exist.

## Steps

Run from `deployment/`, with the machine name of the layout in use (`pc` below):

```powershell
py -3 oblivion.py doctor   --host pc
py -3 oblivion.py validate --host pc
py -3 oblivion.py plan     --host pc          # read-only: shows every setting of tts and the file it came from
py -3 oblivion.py deploy   --host pc          # clones, installs, writes the .env, runs prepare, starts, waits for health
py -3 oblivion.py status   --host pc
```

On Linux or a Raspberry Pi add `--system-deps` to `deploy` (it installs the `apt` packages of the catalogue). `doctor`, `validate`, `plan` and `status` only read; `deploy` writes, so say so and wait for a yes before running it.

Read in the `deploy` output: the line of the `prepare` step of tts (fetching or "ready"), and whether it is a success or a warning.

## Acceptance criteria

- `doctor` and `validate` have no error (warnings are listed in *Notes*).
- `deploy` finishes, the `prepare` step of tts reports the voice ready (not "could not fetch"), and `status` shows tts healthy on port 8002.
- `models/en_GB-alan-medium.onnx` and `.onnx.json` exist in the **deployed** tts folder.

## Verification

The relevant lines of `plan` (tts), `deploy` (the prepare step) and `status`, pasted in *Notes*.

### Result (run on 2026-11-06, Windows 11, with the maintainer's yes for `deploy`)

**Setup, and why it differs from the steps above.** `config/robot.toml` of the deployment repository uses `speaker-on-pc`, which puts tts on the Raspberry Pi (192.168.1.197); `--host pc` would not deploy tts and `--host pi` would reach another machine. The task forbids editing `deployment/config/`, so the check used a throwaway config outside the workspace, passed with `--config`: a copy of `catalogue.toml`, `layouts/`, `services/` and the committed shared-logging wheel (library paths resolve from the **parent of the config folder**, so a `wheels/` folder had to sit beside it), **without `config/local/`** (it holds a key), with `robot.toml` set to `all-in-one`, machine `robot`, and a `machines/robot.toml` that moves the work directory into the session scratchpad (`...\scratchpad\t0112\work`) instead of `~/oblivion`. Commands were `--host robot --config <copy> --service tts`. The catalogue copy is the working one (it carries the maintainer's uncommitted edits to `catalogue.toml`, not part of this plan). Code deployed: `https://github.com/DanielCalvo-Calvicia/tts_microservice.git @ feature_ai_claude_2`, commit `54a6259a`.

**`doctor`:** all `[ok]`: python 3.14 (need 3.11+), git, venv and ensurepip, workdir writable; `[info]` microphone and speaker need a sound device (not relevant to tts). Python picked: the interpreter that runs the tool, **3.14.2** (the brain venv's); the service venv reports 3.14.2.

**`validate`:** the whole host gave 2 errors that are not about tts and come from the throwaway copy (stt needs `OPENAI_API_KEY`, left out on purpose; the first run also failed to find the shared-logging wheel until `wheels/` was placed beside the copy). `validate --service tts` printed `OK`. A warning that ai-agent has no API key is the same cause. Acceptance "no error" holds for tts.

**`plan --service tts`:** `tts native port 8002 https://github.com/DanielCalvo-Calvicia/tts_microservice.git @ feature_ai_claude_2`, settings `LOG_FORMAT=console`, `SERVICE_HOST=127.0.0.1`, `SERVICE_PORT=8002` (all `[computed]`).

**`deploy --dry-run`:** created nothing (the work folder did not exist afterwards).

**`deploy`** (exit 0), relevant lines in order:
```
$ git clone --quiet <url> ...\work\services\tts_microservice
$ git ... checkout --quiet -B feature_ai_claude_2 origin/feature_ai_claude_2

$ ...\venvs\tts\Scripts\python.exe -m pip install --quiet -r ...\work\state\tts.requirements.txt
$ ...python.exe -m pip install --quiet --no-index --no-deps --force-reinstall --find-links ...\wheels shared-logging
$ ...python.exe scripts/fetch_voice.py

Piper voice en_GB-alan-medium is ready
tts: started in its own window (pid 26144)
tts: healthy and available
```
The `prepare` step was a **success, not a warning**. The deployed `models/` holds `en_GB-alan-medium.onnx` (63,201,294 bytes) and `.onnx.json` (4,888 bytes).

**`status`:** `tts  running  healthy and available; feature_ai_claude_2@54a6259a; native`.

**Log of the deployed service** (`work\logs\tts.log`): `Piper voice loaded voice="en_GB-alan-medium" sample_rate=22050`, then `TtsService initialized name="TTS Microservice" engine="PiperSpeechSynthesis"`, then `/health` and `/available` answered 200. No `falling back` line. (Details of the endpoint and log checks belong to T-01.1.3.)

### Findings

1. **Acceptance criteria all met** on the happy path: `doctor` / `validate` clean for tts, `prepare` reported the voice ready, `status` healthy on 8002, both voice files in the deployed folder.
2. **F3 confirmed in practice.** The tool wrote a stripped copy of the requirements to `work\state\tts.requirements.txt` (the `-e ../shared-logging` line removed, the vendored contracts 0.15.0 wheel kept) and installed the `shared-logging` wheel from the committed `wheels/` folder with `--no-index --no-deps --force-reinstall`. (The folder is `wheels/` in the repository, not `libs/`.)
3. **The deployed venv carries the dev tools, as T-01.3 expects:** `pip list` shows pytest 9.2.0, ruff 0.17.4, black 26.10.1, mypy 2.4.1 and httpx 0.28.1 next to fastapi 0.162.0, numpy 2.5.4, onnxruntime 1.31.1, piper-tts 1.8.0, contracts-microservice 0.15.0, shared-logging 0.1.0. This is the baseline T-01.3 must change.
4. **The dry-run under-reports.** It said `write ...\.env (3 variables)`, the real `.env` has 19 (the tool prints only the computed ones in dry-run). Not a defect of tts; noted so nobody reads "3" as the whole file. The dry-run also did not show the `pip install -r` line because the clone does not exist yet; the real run did it.
5. **Windows start opens a console window** for the service ("started in its own window"); the process is left running for T-01.1.3 and stopped after T-01.1.4 (`oblivion.py stop --host robot --config <copy> --service tts`).
6. The throwaway config and work folder live in the scratchpad `t0112` and are removed when T-01.1 is finished.
