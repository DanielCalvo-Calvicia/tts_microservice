# HTTP API of the service

What `python main.py` answers today, checked against the code on 2026-11-06 (`infrastructure/inbound/http/`, `application/services/tts_service.py`, `contracts` 0.16.0 in the working tree). Everything listed is **built**. The only caller in production is Brain's TTS adapter; there is no authentication (NFR-9).

Interactive documentation generated by FastAPI is served at `/docs`, `/redoc` and `/openapi.json`.

## Routes

| Method and path | Purpose | Answer |
|---|---|---|
| `GET /health` | Liveness: `200` whenever the process answers; touches no engine | Envelope, `data: {healthy: true}` |
| `GET /available` | Whether the speech engine works, and whether a fallback voice is speaking | Envelope, `data: {is_available: bool, reason: str or null}` |
| `POST /process/stream/set` | Brain's upload: the text to speak | `202`, an NDJSON ack stream (events) or an envelope (plain text) |
| `GET /process/stream/get` | The audio of the last `set`, as events | `200`, `application/x-ndjson`, open until the service stops |
| `POST /process/stream` | One request, text in, raw PCM16 out | `200`, headerless PCM16 labelled `audio/wav` |
| `POST /process/batch?text=` | One text, the whole audio in one JSON answer | Envelope, `data: ProcessBatchResponse` |

**`reason` of `/available` (built 2026-11-06, [ADR-008](../decisions/ADR-008-fallback-reported-in-available-reason.md)).** It is `null` while the configured engine speaks. When the service started on the pyttsx3 fallback because the Piper voice or `espeak` could not load, `is_available` stays `true` (Brain's preflight must not fail, ADR-006) and `reason` carries a one-line note: `fallback: pyttsx3 instead of <piper|espeak> (<cause>)`, for example `fallback: pyttsx3 instead of piper (Piper voice 'en_GB-alan-medium' is not in models (fetch it with: python scripts/fetch_voice.py from the service folder, or deploy again))`. The cause is the failure text, cut to 200 characters, with a folder named by its last part and the home directory written `~`: no absolute path is shown (the log keeps the full text). `is_available` is `false` with the same `reason` only if the fallback voice itself does not work. `GET /health` does not carry it. Brain reads `reason` only when `is_available` is `false`; the deployment tool shows it as a warning (T-02.2, built 2026-11-06: `healthy and available, warning: <reason>`).

Another method on a known path answers `405`. Every JSON answer (not the streams) uses the envelope `action / status / status_code / message / timestamp / data` (`contracts.api.common.envelope.ApiEnvelope`).

## Audio format

`sample_rate` (default `22050`) and `channels` (default `1`) are query parameters of `set`, `process/stream` and `process/batch`; both must be greater than 0 (`422` otherwise). The engine's own output is converted to that rate and channel count before it leaves the service (`domain/operations/pcm.py`: linear resampling; mono is duplicated to every output channel). Brain asks for 24 kHz mono. The audio is PCM16 little-endian; inside events it is base64 in `bytes_base64`.

## `POST /process/stream/set`: Brain's upload

Two body kinds, told apart by `Content-Type`:

| Body | Meaning | Answer |
|---|---|---|
| `application/x-ndjson` | A live stream of `TTS_INBOUND` events (`contracts.stream.schemas`). A `partial` carries a piece of text; the `completed` that closes a text carries the whole text, and **that** is what is spoken. Partials left when the stream ends without a `completed` are spoken as a last text | `202` and a response that stays open as the ack stream (`UPLOAD_ACK`): `stream_started`, then `input_completed` when the sender ended, or a recoverable `error` (a sender `error` event is reported as such) |
| anything else | Plain text, one utterance per non-empty line, read up front | `202` envelope (`state: accepted`); synthesis continues in the background |

Rules:

- A new `set` **replaces** the previous one: its generator is cancelled, its audio queue is dropped and readers of the old stream see it end. The very first queue is kept, so a reader that connected before any `set` is not lost.
- A blank text is skipped (logged), never an error.
- `set` fixes the audio format of the stream; `get` must not contradict it.
- The response must stay open while the body is uploaded: once an ASGI response completes the server stops delivering the request body.

## `GET /process/stream/get`: the audio

`application/x-ndjson`, `TTS_OUTBOUND` events with a per-stream sequence number (`contracts.stream.codec.EventSequencer`):

| Event | When |
|---|---|
| `stream_started` | First item of every `set`: `sample_rate`, `channels` |
| `partial` | One per audio chunk of a text: `bytes_base64`, `byte_count`, `chunk_index` (1024 frames per chunk) |
| `completed` | One per text, after its partials: `reason: completed`, the whole text's audio in `output_bytes_base64`, `total_bytes`, `chunk_count` |
| `error` | `code: synthesis_failed`, `recoverable: true`: a text could not be synthesized; the stream carries on with the next text. `code: stream_failed`, `recoverable: false`: the stream itself broke |
| `heartbeat` | Every 15 s when nothing arrives (only after `stream_started`) |

If there was no `set` yet, the call waits on the empty queue. The query parameters `sample_rate` and `channels` may be repeated and must match the `set` (`422` otherwise); `keep_open_after_completed` is accepted for compatibility and ignored: the stream always stays open.

## `POST /process/stream`

The body is text, one utterance per non-empty line (read up front). The answer streams headerless PCM16 as it is produced, labelled `audio/wav` (it carries no WAV header, known debt D-3). Response headers: `X-Action`, `X-Status`, `X-Message`, `X-Timestamp`.

## `POST /process/batch?text=...`

`text` is a query parameter. `data` is `ProcessBatchResponse{audio_data_base64, sample_rate, channels}`. It does not touch the shared `set`/`get` queue.

## Errors

Mapped in `infrastructure/inbound/http/http_error_mapper.py`; the envelope's `data` holds the error text.

| Status | Cause |
|---|---|
| `400` | Blank text (`EmptyText`) |
| `422` | Invalid audio format (`InvalidAudioFormat`) or one that differs from the stream's (`AudioFormatMismatch`) |
| `502` | The speech engine failed (`SynthesisFailed`) |
| `500` | Anything else |

An error inside an open stream is an `error` event, not a status code (the status line was already sent).

## Quick check

```powershell
curl http://127.0.0.1:8002/available     # data.reason is null on the configured engine, a "fallback: ..." note otherwise
curl -X POST "http://127.0.0.1:8002/process/batch?text=Good%20evening&sample_rate=24000"
```
